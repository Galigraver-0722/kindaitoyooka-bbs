# 学習パス

> 日本語版です。英語版が正本です: [English](../09-learning-path.md)

このプロジェクトは、JavaScript を少し書いたことがあるが、Web アプリケーションを配備したことはない生徒でも作れるように設計しています。以下の道筋は、コードベースを小さく検証可能な演習の連続に変えます。各週には、コミットできる成果物と、実行できる確認があります。

## 1. 頭の中のモデル

コードに触る前に、この絵を思い浮かべてください。

```text
Browser ──HTTP request──► Next.js server ──query──► SQLite
   ▲                                                   │
   └──────────── HTML response ◄──────── render ◄──────┘
```

- **HTTP** はブラウザとサーバーが話す言語です。メソッド（`GET`、`POST`）、パス、ヘッダー、本文があります。
- **GET** は何かを要求します。データを変更してはいけません。
- **POST** は何かを送信します。このプロジェクトでは必ずリダイレクトで終わります。
- サーバーは Next.js アプリケーションを動かす Node.js のプロセスです。データベースを読み書きできる唯一の存在です。
- **SQLite** はファイル 1 つに保存されるデータベースです。別のデータベースサーバーはありません。
- **Prisma** は TypeScript の呼び出しを SQL に変え、型付きのオブジェクトを返すライブラリです。

ページがおかしいときは、まず 4 つの箱のどれが失敗したかを決めます。サーバーのターミナルとブラウザのネットワークタブを見る方が、当てずっぽうより速く答えに着きます。

## 2. 6 週間の計画

週 6〜8 時間を想定します。週の順番を守り、データベースの週より前に配備を始めないでください。

### 第 1 週 — 動かして、1 か所変える

目標: ターミナルへの慣れ、HTTP の基本、HTML/CSS。

1. Node.js 22 と pnpm を導入する。
2. README のクイックスタートに従い、ホームページが表示されるまで進める。
3. `prisma/seed.ts` でボードの説明を 1 つ変える。もう一度 `pnpm db:seed` を実行し、ボードが重複せず更新されることを確認する。
4. `src/app/page.tsx` でヒーローの見出しを変える。`pnpm dev` を実行して再読み込みする。

**成果物:** ヒーローの文言とボードの説明を変えた 1 つのコミット。
**確認:** `pnpm db:seed` がボードを upsert し、スレッドが存在するときはスレッドを飛ばす理由を説明できる。

### 第 2 週 — コンポーネントとスタイル

目標: React のコンポーネント、props、Tailwind のユーティリティ。

1. `src/app/page.tsx` と `src/components/site-header.tsx` の JSX を読む。
2. 「最近のスレッド行」を `src/components/thread-row.tsx` に切り出し、スレッドを prop として渡す。
3. 固定バッジの色を両方の場所で変え、1 回の編集で両方が変わることを確認する。

**成果物:** 切り出したコンポーネントをホームページで使う。
**確認:** 投稿行のマークアップが重複して残っていない。

### 第 3 週 — ルーティングとサーバー描画

目標: App Router、動的セグメント、サーバーコンポーネント、`params`。

1. `/rules` を静的なページとして追加する。フッターからリンクする。
2. `/b/general` と `/t/<any-id>` を開く。`src/app/b/[slug]/page.tsx` で `params` を await している場所を探す。
3. 既存のクエリを使って、スレッドページのパンくずにボードのスレッド数を表示する。

**成果物:** `/rules` ページと、更新したパンくず。
**確認:** ゲストが読め、HTML のソースに内容がすでに含まれている。

### 第 4 週 — データベースとマイグレーション

目標: SQL の基本、Prisma スキーマ、マイグレーション、トランザクション。

1. `prisma/schema.prisma` を開き、紙にテーブルを描く。`docs/ja/03-data-model.md` と比べる。
2. 演習: `Thread` に `viewCount Int @default(0)` を追加し、`pnpm exec prisma migrate dev --name add_thread_view_count` を実行する。スレッドを開いたときにインクリメントし、スレッドページに件数を表示する。
3. `prisma/migrations/` に生成された SQL を確認する。

**成果物:** マイグレーション、インクリメント、表示。
**確認:** 同じスレッドを 2 回開くと件数が 2 増え、他のフィールドは変わらない。

> 書き込み経路の注意: 閲覧のたびにインクリメントすると、すべての読み取りが書き込みになります。実際の機能にするなら、デバウンスするかまとめて書き込みます。この演習の目的はマイグレーションであり、閲覧カウンターを出すことではありません。

### 第 5 週 — 認証、セッション、セキュリティ

目標: パスワードのハッシュ、Cookie、セッション、認可、CSRF、検証。

1. ログインを 1 回追跡する: フォーム → `/api/auth/login` → `verifyPassword` → `createSession` → `Set-Cookie`。
2. ブラウザで Cookie を確認し、`HttpOnly` が付いていて JavaScript から読めないことを確かめる。
3. `student` アカウントで `/moderation` に到達しようとする。次に、学生の Cookie を使って `curl -X POST` を `/api/posts/<id>/delete` に送り、隠れたボタンだけでなくサーバーが拒否することを確認する。
4. `Origin: https://evil.example` を付けて POST を送り、403 を確認する。
5. Node 標準のテストランナーか Vitest で、`validateTitle` と `safeNextPath` の単体テストを追加する。`//evil.example` と空のタイトルをカバーする。

**成果物:** 検証のテストと、ログイン追跡のメモ。
**確認:** トークンではなく `SHA-256(token)` を保存するとセッションが守られる理由と、`scrypt` が暗号化ではない理由を説明できる。

### 第 6 週 — 配備と運用

目標: 本番ビルド、HTTPS、バックアップ、監視。

1. VPS かローカルの仮想マシンで `docs/ja/07-operations.md` に従う。
2. サイトを HTTPS の背後に置く。
3. バックアップスクリプトを導入し、手動で実行し、復旧演習を行う。
4. わざと壊し（サービスを停止）、ランブックで復旧する。

**成果物:** 動作する HTTPS の URL と、1 回の成功した復旧。
**確認:** 「データベースファイルはどこにあり、昨夜のバックアップはどこにあるか」に答えられる。

## 3. 用語集

定義は検証可能な形で書きます。何が該当し、何が該当しないかを述べます。

**BBS（bulletin board system、電子掲示板）。** 利用者がボードとスレッドに整理されたメッセージを公開し、メッセージが永続して URL で参照できるウェブサイト。グループチャットは BBS ではありません。話題ごとに整理されておらず、後から確実に見つけられないためです。

**ボード（board）。** スレッドを含む名前付きのカテゴリで、安定した URL スラッグを持ちます（例: `/b/study`）。ボードはスレッドではありません。ボード自身は投稿を持ちません。

**スレッド（thread）。** ボード内の、タイトル付きの 1 つの議論。最初の投稿と、時系列に並んだ返信からなります。安定した id（`/t/<id>`）で識別されます。

**投稿（post）。** 1 つのアカウントが 1 回書いたプレーンテキストのまとまり。ちょうど 1 つのスレッドに属します。最初の投稿も、他の投稿と同じ 1 つの投稿です。

**HTTP リクエスト。** クライアントからのメッセージで、メソッド、対象のパス、ヘッダー、任意の本文を含みます。**レスポンス:** ステータスコード、ヘッダー、任意の本文。

**Cookie。** サーバーがブラウザに保存を求め、同じサイトへの以後のリクエストで送り返される小さな名前と値の組。ブラウザは Cookie を暗号化しません。サーバーが暗号化しない限り、中身は読めるものとして扱います。

**セッション。** Cookie に紐づくサーバー側の状態。このプロジェクトでは、ランダムなトークンのハッシュを主キーとするデータベースの行です。行を削除すると、そのトークンを使っているすべての場所でログアウトされます。

**ハッシュ。** 一方向関数。同じ入力からは常に同じ固定長の出力が得られ、出力から入力を逆算できません。パスワードとセッショントークンはハッシュ化され、暗号化はされません。**暗号化**は鍵で元に戻せますが、ハッシュは戻せません。

**ORM（object-relational mapper）。** データベースの行をオブジェクトに対応付け、メソッド呼び出しから SQL を生成するライブラリ。ここでは Prisma が ORM です。

**マイグレーション（migration）。** データベーススキーマへの、バージョン管理されコミットされる SQL の変更。開発中は `migrate dev` が作成し、本番では `migrate deploy` が未適用のものを適用します。

**サーバーコンポーネント。** サーバーだけで動き、データベースを直接読める React コンポーネント。ブラウザ API やイベントハンドラーは使えません。このプロジェクトのほとんどのコンポーネントはサーバーコンポーネントです。

**クライアントコンポーネント。** `"use client"` を付けたコンポーネントで、ブラウザで動きます（サーバーでも事前描画されます）。MVP では必須のものはありません。

**Route Handler（ルートハンドラー）。** `route.ts` からエクスポートされ、`Request` を受け取って `Response` を返す関数。このプロジェクトのすべての書き込みは Route Handler を通ります。

**CSRF（cross-site request forgery、クロスサイトリクエストフォージェリ）。** 別のサイトが、利用者のブラウザに認証済みのリクエストを送らせる攻撃。ここでの防御は `SameSite=Lax` の Cookie と `Origin` の確認です。

**XSS（cross-site scripting、クロスサイトスクリプティング）。** 実行可能なスクリプトをページに差し込む攻撃。このプロジェクトは React を通じてプレーンテキストを描画し、React がエスケープします。`dangerouslySetInnerHTML` は使いません。

**論理削除（soft delete）。** 行を削除済みとして印を付け（`isDeleted = true`）、データベースには残すこと。モデレーションを取り消し可能かつ監査可能にします。反対は物理削除（hard delete）です。

**シード（seed）。** 開発用のデータを挿入するスクリプト。可能な限り冪等にし、デモアカウントのまま本番に対して実行してはいけません。

**配備（deployment）。** 本番ビルド、永続ストレージ、TLS、プロセスマネージャーを備え、安定したアドレスでアプリケーションに到達できるようにすること。ノート PC で `pnpm dev` を動かすのは配備ではありません。

**PII（個人情報）。** `docs/ja/06-safety-and-moderation.md` の第 2 節を参照。判定基準は合理的な識別可能性であり、名前に限りません。

## 4. デバッグの手引き

| 症状 | 最初に見る場所 | よくある原因 |
| --- | --- | --- |
| すべてのページが 500 | サーバーのターミナル、`journalctl -u toyooka-bbs` | データベースがない、`DATABASE_URL` が誤り、未処理のクエリ |
| 「Table does not exist」 | `pnpm db:push` または `migrate deploy` | スキーマが適用されていない |
| スタイルが当たらない | ブラウザのネットワークタブで `.css` の 404 | ビルド未実行、Tailwind クラスの打ち間違い |
| ログインできるのにヘッダーが「Log in」のまま | Cookie のドメイン／`Secure`／`SameSite` | `COOKIE_SECURE=true` のまま HTTP で配信している |
| `/login` でリダイレクトループ | `getCurrentUser` と Cookie の状態 | セッションのない古い Cookie |
| `database is locked` | 長時間動く `prisma studio`、バックアップ、詰まったリクエスト | 同時書き込み。ランブックを参照 |
| フォームを送っても何も変わらない | ネットワークタブのステータスと `Location` | エラーコード付きの検証リダイレクト |

## 6. AI アシスタントとの付き合い方

アシスタントは説明のために使い、判断を任せないでください。

- 新しいコードを頼む前に、既存の流れを追跡してもらう。
- 変更するファイルと行を明示させる。
- 変更の後は、自分で `pnpm lint` と `pnpm build` を実行する。
- 本番の秘密情報、生徒のデータ、データベースのダンプをチャットに貼らない。
- セキュリティに関わる変更では、修正だけでなく攻撃の筋道を説明してもらう。

大切な習慣は、生成された変更を自分が 1 文で説明できることです。説明できなければコミットしません。
