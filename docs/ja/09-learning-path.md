# 学習パス

> 日本語版です。英語版が正本です: [English](../09-learning-path.md)

このプロジェクトは、JavaScript を少し書いたことはあるものの、Web アプリケーションを配備した経験はない生徒でも、作りきれるように組み立てています。以下の道筋は、コードベースを、小さく確かめられる演習の連続に読み替えたものです。各週には、コミットできる成果物と、自分で実行できる確認があります。

## 1. 全体像をつかむ

コードに触る前に、次の図を頭に置いてください。

```text
Browser ──HTTP request──► Next.js server ──query──► SQLite
   ▲                                                   │
   └──────────── HTML response ◄──────── render ◄──────┘
```

- **HTTP** は、ブラウザとサーバーがやり取りするときの言葉です。メソッド（`GET`、`POST`）、パス、ヘッダー、本文で 1 つの要求を表します。
- **GET** は何かを取りに行く要求です。データを変えてはいけません。
- **POST** は何かを送る要求です。このプロジェクトでは、必ずリダイレクトで終わります。
- サーバーは、Next.js アプリケーションを動かしている Node.js のプロセスです。データベースを読み書きできるのはサーバーだけです。
- **SQLite** は、ファイル 1 つに収まるデータベースです。データベース専用のサーバーはありません。
- **Prisma** は、TypeScript の呼び出しを SQL に変え、型の付いたオブジェクトを返すライブラリです。

ページの表示がおかしいときは、まず 4 つの箱のどこで失敗したのかを切り分けてください。サーバーのターミナルとブラウザのネットワークタブを見れば、当て推量よりずっと早く答えにたどり着けます。

## 2. 6 週間の計画

週に 6〜8 時間の学習を想定しています。週は順番どおりに進め、データベースの週より前に配備へ手を出さないでください。

### 第 1 週 — 動かして、1 か所だけ変えてみる

目標: ターミナルに慣れること、HTTP の基本、HTML と CSS。

1. Node.js 22 と pnpm を導入します。
2. README のクイックスタートに沿って進め、ホームページが表示されるところまで確認します。
3. `prisma/seed.ts` でボードの説明を 1 つ変えます。もう一度 `pnpm db:seed` を実行し、ボードが重複せず更新されることを確かめます。
4. `src/app/page.tsx` でヒーローの見出しを変えます。`pnpm dev` を実行して再読み込みします。

**成果物:** ヒーローの文言とボードの説明を変えた 1 つのコミット。
**確認:** `pnpm db:seed` がボードを upsert し、スレッドが既にあるときはスレッドを飛ばす理由を説明できる。

### 第 2 週 — コンポーネントとスタイル

目標: React のコンポーネント、props、Tailwind のユーティリティクラス。

1. `src/app/page.tsx` と `src/components/site-header.tsx` の JSX を読みます。
2. 「最近のスレッド行」を `src/components/thread-row.tsx` に切り出し、スレッドを prop として受け取る形にします。
3. 固定バッジの色を 2 か所とも変え、1 回の編集で両方に反映されることを確認します。

**成果物:** 切り出したコンポーネントをホームページで使っている状態。
**確認:** 投稿行のマークアップが重複して残っていない。

### 第 3 週 — ルーティングとサーバー描画

目標: App Router、動的セグメント、サーバーコンポーネント、`params`。

1. `/rules` を静的なページとして追加し、フッターからリンクします。
2. `/b/general` と `/t/<any-id>` を開きます。`src/app/b/[slug]/page.tsx` で `params` を await している箇所を探してください。
3. 既存のクエリを使って、スレッドページのパンくずにボードのスレッド数を表示します。
4. 画面は最初から日本語で開きます。ヘッダーの切り替えで EN にし、`<html lang>` と日付が変わることを確認してから日本語に戻してください。`src/lib/locales.ts` の 2 つの辞書に文字列を 1 つだけ足して、両方に揃うまで整合性のテストが落ちることも見ておきましょう。

**成果物:** `/rules` ページと、更新したパンくず。
**確認:** ゲストでも読め、HTML のソースに内容がすでに含まれている（ページのソースを表示）。

### 第 4 週 — データベースとマイグレーション

目標: SQL の基本、Prisma スキーマ、マイグレーション、トランザクション。

1. `prisma/schema.prisma` を開き、紙にテーブルを書き出します。`docs/ja/03-data-model.md` と見比べてください。
2. 演習: `Thread` に `viewCount Int @default(0)` を追加し、`pnpm exec prisma migrate dev --name add_thread_view_count` を実行します。スレッドを開いたときにインクリメントし、スレッドページに回数を表示します。
3. `prisma/migrations/` に生成された SQL を確認します。

**成果物:** マイグレーション、インクリメント、回数の表示。
**確認:** 同じスレッドを 2 回開くと回数が 2 増え、ほかのフィールドは変わらない。

> 書き込み経路の注意: 閲覧のたびにインクリメントすると、読み取りがすべて書き込みになります。実際の機能にするなら、まとめて書くか、間引く仕組みを入れてください。この演習の目的はマイグレーションであって、閲覧カウンターを出すことではありません。

### 第 5 週 — 認証、セッション、セキュリティ

目標: パスワードのハッシュ、Cookie、セッション、認可、CSRF、入力の検証。

1. ログインを 1 回だけ追いかけます。フォーム → `/api/auth/login` → `verifyPassword` → `createSession` → `Set-Cookie` の順です。
2. ブラウザで Cookie を確認し、`HttpOnly` が付いていて JavaScript から読めないことを確かめます。
3. `student` アカウントで `/moderation` を開こうとしてみます。次に、学生の Cookie を使って `/api/posts/<id>/delete` に `curl -X POST` を送り、隠れたボタンだけでなくサーバー側でも拒否されることを確認します。
4. `Origin: https://evil.example` を付けて POST を送り、403 が返ることを見ます。
5. Node 標準のテストランナーか Vitest で、`validateTitle` と `safeNextPath` の単体テストを追加します。`//evil.example` と空のタイトルを必ず含めてください。

**成果物:** 検証のテストと、ログインの追跡メモ。
**確認:** トークンそのものではなく `SHA-256(token)` を保存するとセッションが守られる理由と、`scrypt` が暗号化ではない理由を説明できる。

### 第 6 週 — 配備と運用

目標: 本番ビルド、HTTPS、バックアップ、監視。

1. VPS か手元の仮想マシンで、`docs/ja/07-operations.md` に沿って作業します。
2. サイトを HTTPS で公開します。
3. バックアップスクリプトを導入して手動で実行し、復旧演習まで行います。
4. わざと壊します（サービスを停止）。ランブックを見て復旧してください。

**成果物:** HTTPS で公開された URL と、1 回の成功した復旧。
**確認:** 「データベースファイルはどこにあり、昨夜のバックアップはどこにあるか」に答えられる。

## 3. 用語集

定義は、確かめられる形で書きます。何が当てはまり、何が当てはまらないかを述べます。

**BBS（bulletin board system、電子掲示板）。** 利用者が書いたメッセージをボードとスレッドに分けて公開し、そのメッセージが残り続け、URL で指せるウェブサイトです。グループチャットは BBS ではありません。話題ごとに整理されておらず、あとから確実に掘り出せないからです。

**ボード（board）。** スレッドを入れておく名前付きの区分で、`/b/study` のような変わらない URL スラッグを持ちます。ボードはスレッドではありません。ボード自体は投稿を持ちません。

**スレッド（thread）。** ボードの中の、タイトル付きの 1 つの話です。最初の投稿と、時系列に並んだ返信でできています。変わらない id（`/t/<id>`）で指せます。

**投稿（post）。** 1 つのアカウントが 1 回に書いたプレーンテキストのまとまりで、必ず 1 つのスレッドに属します。最初の投稿も、ほかの投稿と同じ 1 つの投稿です。

**HTTP リクエスト。** クライアントから届くメッセージで、メソッド、対象のパス、ヘッダー、省略できる本文を含みます。**レスポンス** は、ステータスコード、ヘッダー、省略できる本文です。

**Cookie。** サーバーがブラウザに保存を頼み、同じサイトへの次のリクエストで送り返される、小さな名前と値の組です。ブラウザが Cookie を暗号化することはありません。サーバー側で暗号化していない限り、中身は読めるものとして扱ってください。

**セッション。** Cookie に結び付いたサーバー側の状態です。このプロジェクトでは、ランダムなトークンのハッシュを主キーにしたデータベースの行がセッションです。この行を消すと、そのトークンを使っているすべての場所でログアウトします。

**ハッシュ。** 一方向の関数です。同じ入力からは常に同じ長さの出力が得られ、出力から入力へは戻せません。パスワードとセッショントークンはハッシュ化するもので、暗号化するものではありません。**暗号化** は鍵があれば元に戻せますが、ハッシュは戻せません。

**ORM（object-relational mapper、オブジェクト関係マッピング）。** データベースの行をオブジェクトに対応づけ、メソッド呼び出しから SQL を組み立てるライブラリです。ここでは Prisma が ORM にあたります。

**マイグレーション（migration）。** データベースのスキーマに対する、版管理してコミットする SQL の変更です。開発中は `migrate dev` が作り、本番では `migrate deploy` が未適用のものを当てます。

**サーバーコンポーネント。** サーバーだけで動き、データベースを直接読める React コンポーネントです。ブラウザの API もイベントハンドラーも使えません。このプロジェクトのコンポーネントは、ほとんどがサーバーコンポーネントです。

**クライアントコンポーネント。** `"use client"` を付けたコンポーネントで、ブラウザで動きます（サーバーでも事前に描画されます）。MVP では必須のものはありません。

**ルートハンドラー（route handler）。** `route.ts` からエクスポートする関数で、`Request` を受け取って `Response` を返します。このプロジェクトの書き込みは、すべてルートハンドラーを通ります。

**CSRF（cross-site request forgery、クロスサイトリクエストフォージェリ）。** 別のサイトが、利用者のブラウザに認証済みのリクエストを送らせる攻撃です。ここでは `SameSite=Lax` の Cookie と `Origin` の確認で防ぎます。

**XSS（cross-site scripting、クロスサイトスクリプティング）。** 実行できるスクリプトをページに紛れ込ませる攻撃です。このプロジェクトはプレーンテキストを React 経由で描画し、React がエスケープします。`dangerouslySetInnerHTML` は使いません。

**論理削除（soft delete）。** 行を削除済みとして印を付け（`isDeleted = true`）、データベースには残しておくことです。モデレーションを取り消せる状態に保ち、あとから検証できるようにします。反対は物理削除（hard delete）です。

**シード（seed）。** 開発用のデータを入れるスクリプトです。できるかぎり冪等にし、デモアカウントのまま本番に対して実行しないでください。

**配備（deployment）。** 本番ビルド、永続ストレージ、TLS、プロセスマネージャーをそろえ、安定したアドレスでアプリケーションに到達できるようにすることです。ノート PC で `pnpm dev` を動かすのは配備ではありません。

**ロケール（locale）。** 画面の文言と書式に使う言語のことです。`locale` Cookie に `en` か `ja` として保存します。ロケールが変えるのは画面の文言、日付、数値の書式だけで、利用者が書いた内容は翻訳しません。

**PII（個人情報）。** `docs/ja/06-safety-and-moderation.md` の第 2 節を参照してください。判断の基準は「合理的に本人を特定できるか」で、名前に限りません。

## 4. デバッグの手引き

| 症状 | まず見る場所 | よくある原因 |
| --- | --- | --- |
| すべてのページが 500 | サーバーのターミナル、`journalctl -u toyooka-bbs` | データベースがない、`DATABASE_URL` が誤っている、未処理のクエリ |
| 「Table does not exist」 | `pnpm db:push` または `migrate deploy` | スキーマが適用されていない |
| スタイルが当たらない | ブラウザのネットワークタブで `.css` の 404 を確認 | ビルドをやり直していない、Tailwind クラスの打ち間違い |
| ログインはできるのにヘッダーが「Log in」のまま | Cookie のドメイン／`Secure`／`SameSite` | `COOKIE_SECURE=true` のまま HTTP で配信している |
| `/login` でリダイレクトがループする | `getCurrentUser` と Cookie の状態 | セッションのない古い Cookie が残っている |
| `database is locked` | 長時間動かしている `prisma studio`、バックアップ、止まったリクエスト | 同時書き込み。ランブックを参照 |
| フォームを送っても何も変わらない | ネットワークタブのステータスと `Location` | エラーコード付きの検証リダイレクト |

## 6. AI アシスタントとの付き合い方

アシスタントには説明をさせ、判断は任せないでください。

- 新しいコードを頼む前に、いまある流れを追跡してもらいます。
- 変更するファイルと行を、必ず示してもらいます。
- 変更したあとは、`pnpm lint` と `pnpm build` を自分で実行します。
- 本番の秘密情報、生徒のデータ、データベースのダンプは、チャットに貼らないでください。
- セキュリティに関わる変更では、修正案だけでなく攻撃の筋道を説明してもらいます。

大事なのは習慣です。生成された変更は、自分の言葉で 1 文に説明できるものでなければコミットしません。
