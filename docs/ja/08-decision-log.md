## ADR-0001 — Next.js によるフルスタックアプリケーション

**文脈。** 保守担当は生徒 1 人。利用者は学校規模。数週間で、理解できて配備できるものを出す必要がある。チームの JavaScript の知識は基本レベルで、時間は限られている。

**決定。** Next.js 16（App Router）と React Server Components、TypeScript、Tailwind CSS を使い、配備可能なアプリケーション 1 つにまとめる。

**結果。**

- コードベース 1 つ、配備 1 つ、言語 1 つ。
- サーバー描画なので、古いスマートフォンでも動き、JavaScript なしでも動く。
- フレームワークの変化は速い。バージョンを上げるときは `node_modules/next/dist/docs/` のローカル文書を読む必要がある。
- チームはサーバーコンポーネントとクライアントコンポーネントの違いを理解する必要がある。

**検討した代替案。**

- *Django や Rails*: 掲示板には最適で、必要なものが揃っている。ただし言語が 2 つになり、インタラクティブな部分には別のフロントエンド工程が要る。
- *Laravel*: 同じトレードオフに加え、PHP のホスティングに慣れていない可能性がある。
- *React SPA + Express API の分離*: 部品が増え、判断も増え、動く掲示板までの時間が長くなる。

**見直す条件。** ネイティブのモバイルクライアント、バックグラウンドジョブ、リアルタイム機能が必要になり、フレームワークに収まらない場合。その場合もデータベースは残し、API を移す。

## ADR-0002 — MIT ライセンス

**文脈。** リポジトリは公開である必要があり、ライセンスの選択をプロジェクトに一任するよう依頼された。利用者は生徒と学校で、商業化の計画はない。

**決定。** MIT ライセンスで公開する（Copyright 2026 Kindai Toyooka BBS contributors）。

**結果。**

- 著作権表示を残せば、誰でも利用、改変、再配布できる。クローズドソースの形でも可能。
- 生徒と学校にとって、最も理解しやすく再利用しやすい。
- 学校や、学校が雇った業者が改変を公開する義務はない。

**検討した代替案。**

- *AGPL-3.0*: ネットワーク越しに提供する場合も改変を公開し続ける。公開フォーラムには合う。v0.1 では、学校にコンプライアンス上の疑問を増やし、貢献者を遠ざけるため見送った。将来、業者の改善を公開させたい場合は、フォークで AGPL を採用できる。既存コードのライセンスは取り消せないが、将来の版は変更できる。
- *Apache-2.0*: 特許の許諾と通知の要件が加わる。学生プロジェクトには法的な文面がやや多い。
- *ライセンスなし*: すべての権利を保留し、誰も法的に再利用できない。公開リポジトリとしては不適切。

**見直す条件。** 営利企業が改変版を有料サービスとしてホストし始めた場合、または学校の法務担当が別のライセンスを求めた場合。

## ADR-0003 — Prisma と SQLite

**文脈。** 想定負荷は、1 校あたり 1 日数百回の読み取りと数十回の書き込み。保守担当にデータベース運用の経験はない。

**決定。** データを SQLite の単一ファイルに保存し、Prisma 経由でアクセスする。

**結果。**

- バックアップはファイルのコピー。ローカル開発にデータベースサーバーは不要。
- Prisma のスキーマがモデルの文書になり、型付きのクエリが使える。
- 書き込みは直列化される。モードによっては長いトランザクションが読み取りを妨げる。
- 水平スケールはできない。1 つのアプリケーションインスタンスがファイルを所有する。
- 後から PostgreSQL へ移す場合は、datasource の変更とマイグレーションで済み、クエリの書き直しは不要。

**検討した代替案。**

- *最初から PostgreSQL*: 同時実行性とマネージドバックアップに優れるが、トラフィックがない段階で、動かし、守り、費用を払うサービスが増える。
- *MySQL*: 運用コストは同じで、このプロジェクトに利点がない。
- *`node:sqlite` を直接使う*: 依存は減るが、SQL を手で書き、スキーマの道具がない。学習用の資料も Prisma より少ない。

**見直す条件。** `database is locked` が繰り返し出る、アプリケーションインスタンスを 2 つ以上にする必要がある、バックアップが遅くなる（`docs/ja/02` の第 9 節を参照）。

## ADR-0004 — 認証プロバイダではなく独自の Cookie セッション

**文脈。** 学校の Google Workspace との連携なし、有料の ID プロバイダなし、長い承認手続きなしで認証を動かす必要がある。

**決定。** `scrypt` によるハッシュ、ランダムなセッショントークン、`HttpOnly` Cookie を使ったユーザー名／パスワード認証を実装する。サーバー側にはトークンのハッシュだけを保存する。

**結果。**

- 外部依存なし、ベンダーの承認なし、完全に理解できるコード。
- パスワード再設定、メール確認、レート制限、アカウント列挙の防御はチームの責任になる。まだ不足しているものもある（`docs/ja/01` を参照）。
- SSO はない。生徒はもう 1 つパスワードを作ることになり、使い勝手とサポートのコストになる。

**検討した代替案。**

- *学校の Google アカウントを使う Auth.js*: 学校が OAuth を許可し、全生徒がアカウントを持っていれば最高の UX。管理者の同意とクライアントシークレットが必要。
- *Clerk／Auth0*: 導入は速いが、継続的な費用がかかり、未成年の生徒の身元データをベンダーが持つ。学校は厳しく質問する。
- *マジックリンク*: 生徒への確実なメール配信が必要で、学校が許可しない場合がある。

**見直す条件。** 学校が全生徒に Google Workspace を導入し、OAuth を承認した場合。移行経路は、`User` テーブルを残し、外部 ID の列を追加することであり、コンテンツの書き直しではない。

## ADR-0005 — 素の HTML フォームと Route Handler

**文脈。** すべての書き込みを、JavaScript フレームワークに邪魔されずにテストし、筋道立てて理解できるようにする必要がある。古い端末でも動く必要がある。

**決定。** 変更は `/api` 以下の Route Handler への HTML `<form>` の POST で行う。ハンドラーは検証し、書き込み、`303` リダイレクトで応答する。MVP ではクライアント側の状態ライブラリも `fetch` も使わない。

**結果。**

- 書き込みの経路全体を `curl` でテストできる。
- JavaScript なしでも動き、段階的に機能を落とせる。
- Server Actions より冗長。フラッシュメッセージはクエリ文字列で運ぶ。
- ライブプレビューや楽観的更新のようなリッチな操作には、後でクライアントコンポーネントが必要になる。

**検討した代替案。** Next.js の Server Actions（定型句は減るが、コマンドラインからのテストが難しい）、GraphQL や tRPC（この規模では不要な迂回）、別の REST API（2 つ目のクライアントができたときだけ有用）。

## ADR-0006 — 英語を正本とし、日本語版の文書を併置する

**文脈。** プロジェクト所有者は、コード、コメント、文書を英語にすることを求めている。学校は日本にあり、生徒の大半は日本語の方を読みやすい。所有者から文書の日本語版を作るよう依頼があった。v0.1 の画面は英語のままである。

**決定。** コード、コメント、画面、コミットメッセージ、Issue、プルリクエストの英語を正本とする。`docs/` が英語の正本であり、`docs/ja/` に同じファイル名と同じ構成で完全な日本語訳を置く。両者が食い違う場合は英語版を優先する。両方の版を同じプルリクエストで更新する。

**結果。**

- 日本の教員、生徒、学校の管理職が、翻訳者を介さずに方針と計画を読める。
- 文書の変更は毎回 2 回行う必要があり、翻訳のずれは現実的な保守コストになる。
- 日本語版でも、コマンド、コードの識別子、URL、エラーコードは英語のままにする。翻訳するとコピー＆ペーストや検索が壊れるため。
- エラーコードの対応表（`src/lib/messages.ts`）は、将来画面自体を翻訳するときの自然な接合点になる。

**見直す条件。** 学校が承認のために日本語の画面を求めた場合、または利用データから英語が生徒の障壁になっていると分かった場合。計画は、ロケール Cookie とメッセージカタログの導入であり、アプリのフォークではない。

## ADR-0007 — すべての利用者コンテンツを論理削除する

**文脈。** モデレーションは取り消し可能で監査可能である必要があり、投稿の削除は周囲の会話を壊してはならない。

**決定。** `isDeleted = true` にしてプレースホルダーを描画する。アプリケーションから投稿やスレッドを物理削除しない。

**結果。**

- モデレーターは、何がなぜ削除されたかを確認できる。
- データベースに有害なテキストが残る。公開前に保存期間に基づく削除が必要（`docs/ja/03` の第 8 節を参照）。
- データベースにアクセスできる強い意志のある利用者は、削除された内容を読める。データベースへのアクセスは保守担当に限られ、監査されるため、これは許容する。

**検討した代替案。** 物理削除（文脈と監査を失う）、UI だけで隠す（行が別の場所で配信されると不十分）、別のアーカイブテーブル（この規模には複雑すぎる）。
