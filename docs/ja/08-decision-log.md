## ADR-0001 — Next.js によるフルスタックアプリケーション

**文脈。** 保守を担当するのは生徒 1 人です。利用範囲は学校規模で、数週間のうちに、理解しやすく配備できるものを出す必要があります。チームの JavaScript の知識は基本レベルで、使える時間も限られています。

**決定。** Next.js 16（App Router）、React Server Components、TypeScript、Tailwind CSS を使い、配備できるアプリケーション 1 つにまとめます。

**結果。**

- コードベースも配備先も 1 つで、言語も 1 つに収まります。
- サーバー描画なので、古いスマートフォンでも動き、JavaScript がなくても表示できます。
- フレームワークの変化は速いペースで進みます。バージョンを上げるときは、手元の `node_modules/next/dist/docs/` にある Next.js 文書を読んでください。
- サーバーコンポーネントとクライアントコンポーネントの違いを、チームが理解している必要があります。

**検討した代替案。**

- *Django や Rails*: 掲示板にはうってつけで、必要な機能がひととおり揃っています。ただし言語が 2 つになり、インタラクティブな部分にはフロントエンドの工程が別に要ります。
- *Laravel*: トレードオフは同じうえ、PHP のホスティングに不慣れな可能性があります。
- *React SPA と Express API の分離*: 部品も判断も増え、動く掲示板にたどり着くまでが遅くなります。

**見直す条件。** ネイティブのモバイルクライアント、バックグラウンドジョブ、リアルタイム機能が必要になり、フレームワークの枠に収まらなくなったときです。その場合もデータベースは残し、API 側だけを移します。

## ADR-0002 — MIT ライセンス

**文脈。** リポジトリは公開が前提で、ライセンスの選択はプロジェクト側に任されています。利用者は生徒と学校で、商用化の予定はありません。

**決定。** MIT ライセンスで公開します（Copyright 2026 Kindai Toyooka BBS contributors）。

**結果。**

- 著作権表示を残せば、誰でも自由に利用、改変、再配布できます。クローズドソースの形に組み込むことも可能です。
- 生徒と学校にとって、いちばん理解しやすく再利用しやすいライセンスです。
- 学校にも、学校が委託した業者にも、改変内容を公開する義務は生じません。

**検討した代替案。**

- *AGPL-3.0*: ネットワーク越しに提供する場合でも改変を公開し続ける条件で、公開フォーラムの性格に合います。v0.1 では見送りました。学校にコンプライアンス上の検討事項が増え、貢献を考えている人の足を遠のかせるためです。将来、業者による改善を公開させたい場合は、フォークで AGPL を採用できます。既存コードのライセンスは取り消せませんが、以後の版は変更できます。
- *Apache-2.0*: 特許の許諾と通知の要件が加わります。学生プロジェクトには法的な文面がやや多めです。
- *ライセンスを定めない*: すべての権利を留保する扱いになり、誰も法的に再利用できません。公開リポジトリとしては不適切です。

**見直す条件。** 営利企業が改変版を有料サービスとしてホストし始めたとき、または学校の法務窓口から別のライセンスの希望が出たときです。

## ADR-0003 — Prisma を使った SQLite

**文脈。** 想定している負荷は、1 校あたり 1 日数百回の読み取りと数十回の書き込みです。保守担当にデータベース運用の経験はありません。

**決定。** データは SQLite の単一ファイルに保存し、Prisma からアクセスします。

**結果。**

- バックアップはファイルのコピーで済み、ローカル開発にデータベースサーバーは要りません。
- Prisma のスキーマがモデルの仕様書代わりになり、型の付いたクエリを書けます。
- 書き込みは直列になります。モードによっては、長いトランザクションが読み取りを止めます。
- 水平スケールはできません。1 つのアプリケーションインスタンスがファイルを占有します。
- 後から PostgreSQL へ移す場合も、datasource の変更とマイグレーションの実行で済み、クエリを書き直す必要はありません。

**検討した代替案。**

- *最初から PostgreSQL*: 同時実行性とマネージドなバックアップに優れますが、アクセスがまだない段階で、動かして守って費用を払うサービスが 1 つ増えます。
- *MySQL*: 運用の手間は同じで、このプロジェクトに利点はありません。
- *`node:sqlite` を直接使う*: 依存は減りますが、SQL を手書きするうえスキーマ用の道具もありません。学習用の資料も Prisma より少なめです。

**見直す条件。** `database is locked` が繰り返し出るとき、アプリケーションインスタンスを 2 つ以上にする必要が出たとき、バックアップに時間がかかるようになったときです（`docs/ja/02` の第 9 節を参照）。

## ADR-0004 — 認証プロバイダを使わず、独自の Cookie セッション

**文脈。** 認証は、学校の Google Workspace との連携なし、有料の ID プロバイダなし、長い承認手続きなしで動く必要があります。

**決定。** `scrypt` によるハッシュ、ランダムなセッショントークン、`HttpOnly` Cookie を使ったユーザー名とパスワードの認証を実装します。サーバー側にはトークンのハッシュだけを保存します。

**結果。**

- 外部依存もベンダーの承認もなく、コードは最後まで読み解けます。
- パスワード再設定、メール確認、レート制限、アカウントの存在を推測されにくくする対策は、チームが自分で持つことになります。まだ実装できていないものもあります（`docs/ja/01` を参照）。
- SSO はありません。生徒はパスワードをもう 1 つ覚えることになり、使い勝手とサポートの負担になります。

**検討した代替案。**

- *学校の Google アカウントを使う Auth.js*: 学校が OAuth を許可し、全生徒がアカウントを持っていれば、使い勝手は最良です。管理者の同意とクライアントシークレットが必要になります。
- *Clerk／Auth0*: 導入は速いものの、継続的な費用がかかり、未成年の生徒の身元データをベンダーが保持します。学校側から厳しい質問が出るのは避けられません。
- *マジックリンク*: 生徒への確実なメール配信が前提になり、学校が認めない場合があります。

**見直す条件。** 学校が全生徒に Google Workspace を導入し、OAuth を承認したときです。移行の道筋は、`User` テーブルを残したまま外部 ID の列を追加する方法で、コンテンツを書き直す必要はありません。

## ADR-0005 — 素の HTML フォームとルートハンドラー

**文脈。** すべての書き込みを、JavaScript フレームワークに邪魔されずに試し、筋道を立てて理解できるようにしたいと考えています。古い端末でも動く必要があります。

**決定。** 変更は `/api` 以下のルートハンドラーへの HTML `<form>` の POST で行います。ハンドラーは内容を検証して書き込み、`303` リダイレクトで応答します。MVP ではクライアント側の状態管理ライブラリも `fetch` も使いません。

**結果。**

- 書き込みの経路全体を `curl` で試せます。
- JavaScript がなくても動き、機能が使えない環境でも破綻しません。
- Server Actions より記述は冗長になります。フラッシュメッセージはクエリ文字列で運びます。
- ライブプレビューや楽観的更新のような凝った操作には、後からクライアントコンポーネントが必要になります。

**検討した代替案。** Next.js の Server Actions（定型コードは減りますが、コマンドラインからのテストが難しくなります）、GraphQL や tRPC（この規模では不要な回り道です）、別立ての REST API（2 つ目のクライアントができて初めて役に立ちます）。

## ADR-0006 — 日本語を既定とする英日バイリンガル画面（正本は英語）

**文脈。** プロジェクトの所有者は、コード、コメント、文書を英語で書くことを求めています。学校は日本にあり、生徒の多くは日本語のほうを読みやすく感じます。所有者からは、日本語版の文書と、アプリ内の言語切り替えの両方が求められました。主に使うのは日本語話者なので、最初から言語を選ばせず、日本語で開くべきです。画面は簡素なまま保ち、クライアント側の JavaScript がなくても動き、有料サービスを増やさないことが条件です。

**決定。** コード、コメント、画面に出す文言の原文、コミットメッセージ、Issue、プルリクエストは英語を正本とします。画面は、`locale` Cookie がないときに日本語で開き、ヘッダーから英語に切り替えられるようにします。利用者に見える文字列はすべて型付きの辞書（`src/lib/locales.ts`）に置き、選んだ言語は有効期限 1 年の `locale` Cookie に保存します。切り替えは `POST /api/locale` のフォームで行い、元のページへリダイレクトして戻します。`docs/` が文書の正本で、`docs/ja/` に完全な日本語訳を置きます。両者が食い違った場合は英語版を優先し、2 つの版は同じプルリクエストで更新します。日本語版でも、コマンド、識別子、URL、エラーコードは英語のままにします。

**結果。**

- 初めて来た人も、言語を選ぶ手間なしに読み始められます。英語で読みたい人は、ヘッダーで 1 回切り替えるだけです。
- i18n 用の依存も、ロケールを前置したルートも、クライアント側での翻訳のちらつきもありません。最初のバイトから、サーバーが正しい言語で描画します。
- 2 つの辞書の形を比べる単体テストがあるので、日本語の文字列が欠けると CI が落ちます。
- 利用者が書いた内容（スレッドのタイトル、投稿、ボード名）は自動翻訳しません。切り替わるのは画面の文言、日付、数値の書式だけです。
- 新しい画面の文言は 2 回追加することになり、文書の変更も 2 回行うことになります。翻訳のずれは、現実的な保守コストになります。
- エラーコードの対応表は、サーバー側のメッセージを翻訳するときの接合点として残ります。

**検討した代替案。**

- *英語を既定にして日本語に切り替える*: 以前の形です。主な読者が日本語話者なのに、まず切り替えボタンを探させてしまうため、やめました。
- *ブラウザの言語に合わせる*: 混在する利用者には便利ですが、正しさの基準がもう 1 つ増え、共用の学校端末では意図しない言語で開くことがあります。見える切り替えのほうが分かりやすいと判断しました。
- *next-intl や next-i18next*: 成熟したライブラリですが、2 言語しかなくローカライズした URL も持たないアプリには、依存とルーティングの作法が増えるだけです。
- *ロケールを前置したルート（`/ja/...`）*: 検索エンジンのインデックスには有利ですが、この学校の掲示板はそこを狙っていません。すべてのリダイレクトと Cookie のパスも複雑になります。
- *クライアント側で翻訳する*: 導入は簡単ですが、誤った言語が一瞬表示され、JavaScript なしでも動くという約束を破ります。

**見直す条件。** 学校が 3 つ目の言語を望んだとき、系列校など別の既定言語が必要になったとき、あるいは検索エンジンにローカライズしたページをインデックスさせる必要が出たときです。移行の道筋は辞書をもう 1 つ増やすことで、必要になった場合に限り、ロケールを前置したルートも選べます。

## ADR-0007 — 利用者が書いたコンテンツはすべて論理削除

**文脈。** モデレーションは取り消しができ、あとから検証できる必要があります。投稿を消すときに、周りの会話まで壊してはいけません。

**決定。** `isDeleted = true` を立てて、プレースホルダーを表示します。アプリケーションから投稿やスレッドを物理削除することはしません。

**結果。**

- モデレーターは、何が、なぜ削除されたのかをあとから確認できます。
- データベースには有害なテキストが残ります。公開前に、保存期間に応じた削除が必要です（`docs/ja/03` の第 8 節を参照）。
- データベースにアクセスできる利用者は、削除された内容をなお読めます。データベースへのアクセスは保守担当に限られ、記録を残しているため、この点は許容します。

**検討した代替案。** 物理削除（文脈と検証の記録を失います）、画面だけで隠す（行が別の場所から配信されると足りません）、別のアーカイブテーブル（この規模には複雑すぎます）。

## ADR-0008 — 人気順は透明な重み付きスコアで決める

**文脈。** 読者は注目されているスレッドを見つけたいと考えています。ただし、このサイトは閲覧数を保存しておらず、分析も入れていません。学校の掲示板である以上、並び順の理由は生徒にも教員にも説明できる必要があります。

**決定。** 人気度をアプリケーション側で `いいね × 3 + 保存 × 2 + 返信数 + 直近 72 時間の活動への加点（最大 3）` として計算します。候補は最大 100 件をメモリ上で並べ替え、スコアそのものは保存しません。

**結果。**

- 計算式を公開でき、誰も「人気」の意味を推測しなくて済みます。
- 閲覧者を追跡しなくても、いいねと保存が意味のある信号になります。
- コストは 100 件の上限で頭打ちになります。一方、その窓の外にある古いスレッドは順位付けの対象外です。
- 固定したスレッドは、スコアに関係なく先頭に残ります。

**検討した代替案。** 閲覧数（プライバシーの負担が大きく、水増ししやすい）、Hacker News 式の時間減衰（説明が難しい）、`hotScore` 列の保存（書き込み経路が増え、値がずれやすい）。

**見直す条件。** 候補が数百件を超えたとき、または個別化された並び順が必要になったときです。そのときは SQL 側の集計か、保存したスコアへ移します。

## ADR-0009 — タグは本文ではなく専用の入力欄から取る

**文脈。** 利用者はタグを使いたいと考えていますが、入力欄を増やすのは負担です。本文はこれまでどおりプレーンテキストです。

**決定。** タグは、投稿フォームと返信フォームにある専用の `tags` 欄から取ります。スペース、カンマ、読点で区切り、先頭の `#` は任意です。NFKC で正規化して小文字にし、Unicode の文字・数字・アンダースコアを許し、1 回の書き込みにつき最大 5 個まで残します。`Tag` を共有して作成し、スレッドに結び付けます。タグのリンクは `/search?tag=...` を開きます。本文はタグのために走査しません。

**結果。**

- タグが明示的になります。本文中の `#` は本文のままで、タグにはなりません。
- 打ち間違いは新しいタグとして残ります。改名や統合の画面はまだありません。問題になったらデータベース側で統合します。
- タグは投稿ではなくスレッド全体に付きます。
- タグも利用者が書いた内容です。不適切なタグは、そのタグを最初に付けた投稿を通報してください。

**検討した代替案。** 本文からハッシュタグを解析する方式（最初の実装。`#` が本文なのかメタデータなのか読者に分からないためやめた）、候補付きのタグ選択 UI（データはきれいになるが、UI とクライアント側 JavaScript が増える）、投稿単位のタグ（より細かいが、このサイトではスレッドが発見の単位）。

**見直す条件。** タグの荒らしが出たとき、または教科や部活動のような統制語彙が必要になったときです。

## ADR-0010 — プロセス内の固定ウィンドウでレート制限する

**文脈。** 最初に現実になる悪用は、分散したボットではなく、Enter キーの押しっぱなし、共有パスワードの総当たり、通報の連打です。配備は Caddy の後ろの Node プロセス 1 つで、Redis はありません。

**決定。** `src/lib/rate-limit.ts` に固定ウィンドウのカウンターを `Map` で持ちます。ログイン（IP + ユーザー名）、登録（IP）、スレッド作成、返信、通報、いいね、保存に適用し、超えたら `error=rate-limited` を付けてリダイレクトします。

**結果。**

- 依存も追加サービスもなく、制限値は読んで調整できます。
- 再起動でカウンターが消え、複数インスタンスでは共有されません。
- IP を回す相手には弱いままです。事故と軽い悪用は止められますが、ボットネットは止められません。

**検討した代替案。** Redis のトークンバケット（トラフィックがない段階では運用コストが高い）、データベースのカウンター（リクエストごとに書き込み競合）、プロキシだけの制限（アカウントを見られない）。

**見直す条件。** アプリのインスタンスを 2 つ以上にするとき、またはベータで組織的な悪用が見えたときです。

## ADR-0011 — 公開語彙リストによる助言的な自動フラグ

**文脈。** モデレーターがすべての投稿を読むのは無理で、学校としては嫌がらせ、性的内容、脅迫の早期警告が欲しい。モデルの訓練は範囲外で、生徒の文章を第三者の API に送るのも避けたい。

**決定。** CC BY 4.0 の `naughty-words`（LDNOOBW）の日本語・英語リストを使います。学校で普通に使う語は除外リストで外し、日本語の脅迫語を少し足します。日本語は部分一致、英語は単語境界で照合し、一致したら `source = AUTO` の `Report` を作ります。投稿を隠したり拒否したりはしません。

**結果。**

- 外部サービスも訓練データも不要で、リストは差し替えられます。
- 誤検出は想定内です。特に健康・生物の語彙で起こるので、モデレーターが却下します。キューには一致語が見えます。
- これは人間のための安全網であり、判断者ではありません。

**検討した代替案。** ホスト型のモデレーション API（プライバシー、費用、未成年のデータ）、訓練済み分類器（データと保守の負担）、一致したらブロック（誤検出が正当な質問を黙らせる）。

**見直す条件。** 誤検出が多すぎる、または学校が分野別の方針を求めたときです。そのときは分野別のリストと重みを足します。

## ADR-0012 — モデレーション操作の追記専用監査ログ

**文脈。** モデレーターは投稿を削除し、スレッドをロックします。生徒と担当教員には「誰が何をしたか」の記録が必要で、保守担当には事故調査の材料が要ります。

**決定。** `AuditLog` テーブルを追加し、モデレーションの変更と同じトランザクションで 1 行書きます。行為者、操作、対象、小さな JSON の詳細を記録し、`/moderation` に直近 30 件を表示します。

**結果。**

- すべての変更に説明責任があり、監査行の書き込みに失敗すれば変更もロールバックされます。
- ログは追記のみで、編集・削除の UI はありません。
- 監査テーブルに投稿本文も IP アドレスも入れません。行動の記録であり、監視ではありません。

**検討した代替案。** アプリケーションログだけ（検索できず、失われやすい）、完全なイベントソーシング（この規模には過剰）。

**見直す条件。** 学校が調査のために監査ログの持ち出しを求めたときです。行を編集するのではなく、読み取り専用のエクスポートを足します。

## ADR-0013 — 投稿後 15 分に限る作成者の編集と、「編集済み」の表示

**文脈。** 投稿の直後に、誤字や日付の間違い、教室名の書き間違いに気づくことがあります。編集できないと、間違えたままにするか、訂正の返信を足すしかなく、最初の版がスレッドの先頭に残ります。かといって無制限に編集できると、他の人が返信したあとでスレッドの前提を書き換えられ、モデレーションや引用の根拠が崩れます。

**決定。** スレッドを編集できるのは作成者だけで、`Thread.createdAt` から 15 分以内に限ります。対象はタイトル、最初の投稿、タグ一式です。保存すると `Thread.editedAt` を設定し、スレッドページに時刻付きの「編集済み」を表示します。ロック中と削除済みのスレッドは編集できません。モデレーターは削除とロックの専用操作を使います。

**結果。**

- 小さな間違いは、訂正の返信を増やさずにその場で直せます。
- 読む人には、変更されたことが分かります。変更前の文面までは見えません。
- 最初の投稿より後の返信は、この段階では編集できません。15 分の窓は、会話を書き換えるためではなく、スレッドの前提を直すためのものです。
- 判定は純粋関数 `canEditThread` 1 つにまとめ、境界をテストしています。ページ、ルート、テストが同じ規則を見ます。

**検討した代替案。** 編集を認めない（問い合わせが増え、誤りが残る）、無制限の編集（返信後の書き換えを許す）、差分付きの改訂テーブル（監査は良いが、この段階では UI と保存量が過剰）、誰でも編集できる Wiki 方式（モデレーションの危険）。

**見直す条件。** 返信も編集したいという声が出たとき、またはモデレーターが 15 分を過ぎたタイトルを直す必要が出たときです。どちらも別の決定として扱い、単に窓を広げないでください。

## ADR-0014 — メールによる再設定ではなく、手作業のパスワード復旧

**文脈。** アカウントはユーザー名と任意のメールアドレスで作ります。学校が、サイトから届くメールを生徒全員が読めることを保証できるとは限りません。メール送信事業者を入れると、事業者との契約、未成年のアドレスへの同意、到達性の作り込みが必要になります。それでも、パスワードを忘れた生徒を永久に締め出すわけにはいきません。

**決定。** 保守担当向けのコマンド `pnpm reset-password <username>` を用意します。16 文字のパスワードを生成し、`scrypt` のハッシュだけを保存し、そのアカウントの全セッションを削除して、パスワードを一度だけ表示します。本人確認は対面または担当教員を通して行い、公開スレッドからの再設定依頼は受け付けないと文書に定めます。

**結果。**

- メール送信事業者も確認トークンも要らず、新しい個人情報も増えません。
- 復旧は保守担当が対応できるときに限られます。運用文書に、代わりの担当者を名前で書いておく必要があります。
- 生成したパスワードは、端末と会話を通ります。一度だけ使うものとして扱い、漏れたら再設定をやり直すよう手順に書いています。
- 認証情報の漏えい時にも、同じコマンドが非常口になります。

**検討した代替案。** メールの再設定リンク（利用者自身で完結するが、配信とプライバシーの壁がある）、秘密の質問（弱く、個人情報を増やす）、モデレーターが画面からパスワードを設定する（信頼の境界が広がり、端末側の記録も残らない）。

**見直す条件。** 学校が全生徒にドメインを用意し、メール配信を承認したときです。そのときは `PasswordReset` トークンのテーブルを足し、このコマンドは非常口として残します。

## ADR-0015 — スレッドを開いたときに書く、スレッド単位の既読記録

**文脈。** 生徒は、すべてのボードを読まなくても、どのスレッドが新しいかを知りたい。閲覧数やアクセス解析では別の問いに答えることになり、必要以上のデータを集めます。

**決定。** 利用者とスレッドの組ごとに `ThreadRead` を 1 行置き、`lastReadAt` を保存します。スレッドを開いたときに upsert します。一覧では、行がないとき、または `lastPostAt` が `lastReadAt` より新しいときに「新着」と表示します。ゲストは既読状態を持たず、バッジも出しません。

**結果。**

- バッジが示すのは閲覧ではなく返信の有無で、小さなテーブル 1 つで済みます。
- スレッドページは GET で書き込みます。冪等で、保存するのは時刻だけですが、閲覧がデータベース上は読み取り専用でなくなるということです。
- 既読状態はアカウントごとです。共用端末では、ログイン中のアカウントの状態だけが見えます。
- 「すべて既読にする」操作や、ボードごとの未読件数はまだありません。

**検討した代替案。** `lastVisitedAt` の Cookie（スレッド単位にならず、端末をまたげない）、閲覧数の記録（プライバシーの負担が大きく、水増ししやすい）、週次のダイジェストメール（送信事業者が要る。フェーズ 2 の未完了項目として残る）。

**見直す条件。** 書き込み量が問題になったとき、または「すべて既読」が欲しいという声が出たときです。そのときは upsert をまとめるか、利用者とボードごとの最終閲覧時刻へ移します。

## ADR-0016 — 番号付きのボードページ送り、1 ページ 20 件

**文脈。** ボードのスレッドは、いつかスクロールでは追えない量になります。このサイトはクライアント JavaScript なしでも動く必要があり、人気順は SQL ではなくアプリケーション側で計算しています。

**決定。** ボードページは `?page=N` の番号付きで、1 ページ 20 件にします。ページ番号は最後のページを超えたら丸め、ページ 1 は `page` を付けない URL を正とします。新着順はデータベースの `skip`/`take` を使い、人気順は上位 100 件を並べ替えてから切り出します。固定スレッドは先頭のままです。

**結果。**

- リンクを共有でき、JavaScript なしで動きます。ブラウザの戻る操作も自然です。
- オフセット方式なので、ページを見ている間に新しいスレッドが増えると、項目が重複したり飛んだりすることがあります。この規模では見た目の問題で、正しさの問題ではありません。
- 人気順は上位 100 件だけが対象です。古いスレッドは新着順と検索からたどれます。
- 各ページが読む既読状態は、表示する 20 件分だけです。

**検討した代替案。** `lastPostAt` によるカーソル方式（無限スクロールには向くが、固定スレッドと計算した人気スコアを組み合わせにくい）、「もっと見る」ボタン（クライアント JavaScript が要る）、全件を描画して CSS で隠す方式（無駄が多く、古い端末に厳しい）。

**見直す条件。** 1 つのボードが数千スレッドを常に超える、オフセットの問い合わせが遅くなる、無限フィードが欲しくなる、のいずれかです。そのときは新着順をカーソルへ移し、人気順は番号付きのまま残します。

## ADR-0017 — 方針文を二言語・版管理されたコードとして持つ

**文脈。** 学校の承認には、プライバシー通知、コミュニティルール、モデレーション方針が必要です。文面はコードの実際の動きと一致していなければならず、画面の両言語で存在する必要があります。コードができない削除を約束する方針は、方針がないより悪いものです。

**決定。** 3 つの文書を型付きのモジュール（`src/lib/policies.ts`）に置き、1 つのコンポーネントから `/rules`、`/privacy`、`/moderation-policy` として表示します。英語と日本語は隣り合って置き、更新日を共有し、テストで構造と未記入のプレースホルダーを確認します。アカウント停止や自動削除のように、まだできないことは、できるように書かずに「まだない」と明記します。

**結果。**

- 動作の変更と、それに対応する方針文の変更が同じコミットに入ります。
- 両言語が常にそろい、英語だけの文書が黙って残ることはありません。
- 文面の編集には開発者と配備が必要で、担当教員が直接編集することはできません。公開前の文面の承認は、別途必要です。
- テストが見つけられるのは節の欠落やプレースホルダーであり、法的な妥当性ではありません。

**検討した代替案。** Markdown ファイル（編集は楽だが、二言語がずれやすい）、CMS やデータベース管理のページ（依存、権限、版管理の問題が増える）、方針を最初の案内スレッドにだけ書く（残らず、フッターからリンクしにくい）。

**見直す条件。** 開発者以外が定期的に文面を更新する必要が出たとき、または学校が署名付きの版管理された文書を求めたときです。そのときは版管理された Markdown とレビュー手順へ移し、URL は変えません。

## ADR-0018 — アクセント 1 色の編集者風・スイス様式の視覚体系

**文脈。** 最初の画面は足し算で育ちました。角丸のカード、影、ピル型のバッジ、そして indigo・rose・amber・emerald の競合する色です。どの画面も単体では動いていましたが、ページをまたぐリズムがなく、メタ情報が本文と競い、学校の冊子ではなく一般的なダッシュボードのように見えていました。

**決定。** `src/app/globals.css` に小さな視覚体系を 1 つ置きます。暖かい中性色の背景（`#FAF9F6`）、白は入力欄と必要な面だけ、濃いインク色の本文、低彩度の緑 1 色をアクセントにし、カードの代わりに細い罫線を使います。画面と本文はシステムのサンセリフ 1 系統、数字・日付・ラベル・コードは等幅 1 系統です。レイアウトは 12 カラムのグリッド、広い縦余白、番号付きのリスト、左揃えの文字組みに従います。ホバーは色とごく薄い行の背景だけを変え、内容の行は浮き上がり・拡大・影を使いません。唯一浮かせるのは投稿用のフローティングボタンで、本文から分離する必要があるためです。ページ遷移には 220ms のフェードと 6px の移動を入れ、`prefers-reduced-motion` では無効にします。補助文字は基準色より一段暗くし、12〜13px のメタ情報が WCAG AA を満たすようにしています。

**結果。**

- 内容が前に出ます。タイトル、本文、日付の順が明確で、アクセント色は希少になります。
- 外部フォントを読み込まないため、最初の描画が速く、オフラインでも崩れません。
- 新しい画面は同じ部品を使う必要があります。2 色目のアクセントやカードを足すときは、新しいユーティリティを増やすのではなく、意図して決めることになります。
- 見た目は意図的に静かです。装飾で驚かせるためのものではありません。
- 意味が一意な操作はアイコンを優先します（ブックマーク、検索、返信数）。説明が要る操作にはラベルを残します。

**検討した代替案。** コンポーネントライブラリ（速いが、どのサイトも同じダッシュボードになる）、白黒だけのスイス様式（冷たく、操作の合図が弱い）、アクセント色を増やす（雑然とする）、ダークテーマ（別途アクセシビリティとコントラストの検証が必要。求められたら後で）。

**見直す条件。** 学校の視覚 identity が別の色を求めたとき、またはダークテーマの要望が出たときです。トークンは 1 か所にあるので、ページのマークアップを変えずにテーマを足せます。

## ADR-0019 — リアクションのプログレッシブ・エンハンスメント

**文脈。** いいねと保存は即座に反応してほしい。一方で、このサイトはクライアント JavaScript なしでも動くことを約束しており、既存の書き込みはすべて HTML フォームです。

**決定。** フォームを正とし、クライアントコンポーネント 1 つで強化します。JavaScript があるときは、リクエストの前にアイコンと件数を切り替え、`Accept: application/json` を送り、ルートハンドラーが返す `{active, count}` と突き合わせます。失敗したら状態を戻し、短いエラーをその場に出します。JavaScript がなければ、同じフォームがそのまま POST し、ページを再読み込みします。

**結果。**

- 回線が良ければ即座に反応し、悪ければ正直に戻ります。
- ルートハンドラーは 2 つの応答モードを持つので、両方を `docs/ja/04` に書いています。
- 古い端末でも、スクリプトを止めていても使えます。
- リクエスト中の連打は止めます。キューは実装していません。

**検討した代替案。** フォームを捨ててクライアント状態だけにする（JavaScript なしの約束を破る）、SPA にする（ボタン 2 つのためには過剰）、サーバーアクション（curl での確認がしにくい）。

**見直す条件。** 楽観更新が必要な操作が増えたときです。そのときは、各ボタンに同じ処理を写すのではなく、共通のリクエスト補助関数に切り出します。

## ADR-0020 — 一覧はフィード 1 つ、板のページは 1 つ

**文脈。** 最初の実装では一覧が 4 つに分かれていました。ホームの新しいスレッド、`/threads` の一覧、`/search` の結果、`/bookmarks` の保存一覧です。さらに板ごとの一覧が重なるので、同じスレッドに 3 か所から、それぞれ違う並び順の状態でたどり着けました。試した生徒からは「全部が見られる場所はどこか」と聞かれ、「急上昇」の置き場所も決まっていませんでした。Reddit も掲示板も、範囲ごとに 1 つの並び順付き一覧でこれを解いています。

**決定。** `/` を横断する唯一の一覧にします。3 つの並び（`latest`・`hot`・`rising`）と 3 つの絞り込み（`all`・`saved`・`mine`）、そして検索欄をここに置きます。`/b/[slug]` は板ごとの唯一の一覧で、同じ並べ替えの操作を持たせます。`/threads`、`/search`、`/bookmarks`、`/boards` はクエリを引き継ぐリダイレクトとして残し、古いリンクやブックマークでも同じ表示に着地させます。スレッド作成の入口は右下の ＋ だけです。板のページから開いたときは、その板を選択済みにします。板の一覧は左の欄とモバイルのドロワーに置き、専用のページは作りません。

**結果。**

- 「新しいもの」「人気のもの」「保存したもの」はすべて同じページのクエリの違いになり、並び順と絞り込みの状態が常に見え、そのまま共有できます。
- フィードは最大 30 件です。読むための面であって、過去を全部たどる場所ではありません。深くたどるのは板のページの番号付きページ送りが担います。
- リダイレクトとして 4 つの URL が残り続けます。どれも 3 行で、`docs/ja/04` に書いてあります。
- 板のページとフィードが並べ替えのラベル、スレッドのカード、ブラウザーでの振る舞いを共有するので、「ここだけ見た目が違う」という種類の不具合が起きにくくなります。

**検討した代替案。** `/threads` を 2 つ目の高機能な一覧として残す（直す場所が 2 つ、説明する状態も 2 つ）。板のページをやめて 1 つの一覧に板の絞り込みチップを付ける（バナー・説明・参加人数・提案タグという板の身元の置き場所がなくなる。このサイトは板で組織しています）。急上昇専用の「見つける」ページを作る（3 つ目の並べ替えタブで足り、新しいルートは要りません）。

**見直す条件。** フィードが数百件を超えて本当のページ送りが必要になったとき、またはタグ横断の一覧が求められたときです。どちらもクエリとページ操作の追加で済み、新しいページは要りません。

## ADR-0021 — 生徒が承認を待たずに自分のボードを作れる

**文脈。** 部活やクラスの集まりから、ボードがほしいという声が繰り返し出ていました。当初は教職員だけがボードを作り、承認待ちの列に並べる計画でしたが、新しい部活ができるたびに数日止まり、承認の仕事が 1 人の教員に集まります。スキーマはすでに公式とコミュニティを分けて持っています。

**決定。** ログイン済みの生徒なら誰でも `/boards/new` から `COMMUNITY` ボードを作れます。名前、slug、説明、任意の提案タグを入れます。サイトの形を保つために制限を置きます。1 アカウント 3 件まで、1 時間 5 件まで、slug は一意で予約されたルートと衝突できません。公式ボードは `kind = OFFICIAL` のままで所有者を持ちません。板のページには「コミュニティ」のバッジを出すので、生徒が作った板を公式と取り違えることはありません。

**結果。**

- 部活が願い出たその日の午後に、自分たちの場所を持てます。教職員を待たせません。
- 存在する前に承認する仕組みではないので、モデレーション側は新しい板を後から知ることになります。監査ログと通報の列がその受け皿です。
- 乱用は 2 つの制限で抑えます。加えて、板は他人の投稿を消せません。その権限は全体のモデレーター役に残します。
- 所有者向けの画面はまだありません。自分の板の名前の変更・アーカイブ・削除は、生徒にも教職員にも未実装です。スキーマには `isArchived` があるので、次に作るのはその画面です。

**検討した代替案。** `approvalStatus` 列を持つ承認制（安全だが、状態遷移と教職員向け画面と待ち時間が増える。今日お知らせを出したい部活には重い）。教職員だけが作る（所有の概念は不要だが、すべての部活で 1 人の教員が詰まる）。コミュニティボードを作らない（生徒はグループチャットに戻る。このサイトが置き換えようとしているのはまさにそれです）。

**見直す条件。** 作られた板が嫌がらせやスパムに使われたとき、または板の数が左の欄に収まらなくなったときです。最初の対応は教職員側でのアーカイブで、スキーマは移行なしでそれを支えます。

## ADR-0022 — 全文検索エンジンを入れず、`LIKE` と公開された重みで検索する

**文脈。** フィードの検索はタイトル・タグ・本文への `contains` で、`lastPostAt` 順に 30 件まででした。前学期の質問でも、言葉が完全に一致していれば 30 件の枠に入るとは限らず、「書いたことは残り、あとから来た人が読める」という中心の約束が崩れていました。素直な解決は SQLite FTS5 ですが、同梱のトークナイザーは日本語に合いません。`unicode61` は CJK の連続を 1 トークンとして扱うため「数学」で「中間テストの数学」に当たらず、`trigram` は 3 文字必要なため、よくある 2 文字の語が 0 件になります。

**決定。** 再現率は `LIKE` に任せ、順位付けとページ送りをアプリケーションへ移します。

- 検索語があるときの候補は、表示中の一致すべて（順位付けのため最大 500 行）。直近 30 件ではありません。
- `src/lib/search.ts` が、タイトル一致（各 5、最大 3 か所）、タイトル完全一致（12）、タグ一致（各 3）、本文一致（各 1、最大 5 か所）、わずかな反応数で点数を付けます。同点は `lastPostAt` の新しい順です。
- 結果は 1 ページ 20 件で、一致件数を見出しに出します。検索語のないフィードは 30 件のままです。

**結果。**

- 2 文字の日本語でも見つかり、順位の理由を「タイトルに数学とある」と読者に説明できます。`bm25` の点数ではそれはできません。
- 費用は一致数に比例します。`LIKE` がスレッド表を走査し、候補の本文を 1 リクエストにつき 1 回まとめて取ります。数千スレッドまでは十分で、数十万件には向きません。
- 重みはコードなので、変更は差分で確認でき、単体テストで固定できます。
- 候補 500 行の上限は意図した線です。それ以上一致する語では新しい 500 件だけを順位付けします。件数が増える前に最初に上げるつまみであり、FTS へ置き換える境界でもあります。

**検討した代替案。** `trigram` の FTS5（2 文字検索が壊れる）、`unicode61` と辞書（日本語の分割器という依存が増える）、外部検索サービス（学校のサーバーに可動部分が増える）、変更しない（約束が壊れたまま）。

**見直す条件。** スレッドがおよそ 5,000 件を超えたとき、検索の p95 が 300ms を超えたとき、重みの表では答えられない検索品質の不満が出たときです。

## ADR-0023 — 制限カウンターは SQLite に置き、信頼できるプロキシのときだけヘッダーを読む

**文脈。** 制限はプロセス内の `Map` でした。再起動で全カウンターが消え、アプリを 2 つ動かせばそれぞれが別に数えます。さらに `X-Forwarded-For` の先頭を無条件に読んでいたため、アプリへ直接届くクライアントはリクエストごとにヘッダーを変えて、いくらでも新しいバケットを得られました。

**決定。** カウンターは `RateLimit` テーブルに置き、1 回の呼び出しにつき 1 本の upsert で更新します。

```sql
INSERT ... ON CONFLICT(key) DO UPDATE SET count = CASE WHEN resetAt <= now THEN 1 ELSE count + 1 END
```

期限切れの行はログインのたびに掃除します。クライアントアドレスは `TRUST_PROXY=1` のときだけ `X-Forwarded-For` から読みます。無効のときは全リクエストが同じアドレスを共有するので、IP 単位の制限は意図的に厳しくなり、アカウント単位の制限（ユーザー名ごとのログイン、返信、リアクション）はそのまま効きます。

**結果。**

- 再起動しても攻撃者の試行回数は戻らず、2 つのプロセスが同じウィンドウを共有します。
- 制限の呼び出しごとにデータベースへの書き込みが 1 回入ります。学校の規模では見えませんが、毎秒数千リクエストの設計ではありません。
- 直接公開している場合、IP 単位の制限は 1 つの全体バケットに潰れます。これは安全側の倒し方で、配備テンプレートは Caddy の背後で `TRUST_PROXY=1` を設定します。Caddy はヘッダーを上書きします。
- Redis も新しいサービスも要りません。学校がバックアップするファイルは SQLite 1 つだけです。

**検討した代替案。** メモリのまま（安いが、指摘された 2 点は残る）、Redis の追加（導入・保護・バックアップの対象が増える）、ヘッダーを常に信頼（現在の脆弱性そのもの）、IP 単位の制限をやめる（登録とログインの総当たりが無制限になる）。

**見直す条件。** 別ホストに 2 台目を足すとき、またはプロキシなしで公開するときです。前者は共有ストア、後者はコードではなくプロキシ側の修正が必要です。

## ADR-0024 — ボードの寿命は管理者が持ち、静かなボードは自動でアーカイブする

**文脈。** モデレーターと管理者の権限は同じ（`isModerator`）で、2 つの役割は境界ではなくラベルでした。また「90 日動きのないコミュニティボードはアーカイブする」という約束は実装がなく、`Board.isArchived` は読まれるだけで、書かれる場所がありませんでした。

**決定。** 役割を範囲で分けます。

- `MODERATOR` は日々の仕事を持ちます。投稿の削除、スレッドのロック、通報の処理です。
- `ADMIN` はさらにフォーラムの形を決めます。ボードのアーカイブと復元（`POST /api/boards/[id]/archive`）です。
- 毎日の `pnpm archive-boards` が、表示中の最新スレッドが `BOARD_ARCHIVE_DAYS`（既定 90 日）より古いコミュニティボードをアーカイブし、監査ログを 1 行書きます。`--dry-run` は変更内容を表示するだけです。`/moderation` は管理者にボード一覧とアーカイブ／復元のボタンを見せます。

**結果。**

- モデレーターが部活のボードを黙って閉じることはできません。誰が行ったかは監査ログに残ります。
- アーカイブは画面から戻せて、スレッドはすべて読めるままなので、取り返しのつかない決定ではありません。
- スケジューラーは cron です。アプリ内のタイマーではないので、ホストが止まれば走らず、実行はログファイルに残ります。既存のバックアップと同じ形です。
- スレッドが 1 本もないボードは自動ではアーカイブされません（比較する活動時刻がないため）。新しい部活のボードは、使われるか管理者が動くまで場所を保ちます。

**検討した代替案。** モデレーターにもアーカイブを許す（境界がなくなる）、リクエスト処理の中でアーカイブする（運の悪いリクエストが費用を払う）、cron ではなく systemd timer（ユニットが増える。バックアップで既に cron を案内している）、静かなボードを物理削除する（このプロジェクトが残そうとしている履歴を壊す）。

**見直す条件。** 90 日が短いという声が出たとき、または卒業する代のボードを管理者がまとめてアーカイブしたくなったときです。どちらも設定とスクリプトの引数で足ります。

## ADR-0025 — 通知の受信箱は既存の行から組み立てる

**文脈。** 返信・コメント・いいね・保存をまとめた受信箱をヘッダーに置いてほしいという要望がありました。素直な設計は `Notification` テーブルを作り、出来事のたびに書き込むことです。ただし 5 つの書き込み経路に手を入れる必要があり、既存分の埋め戻しも要り、要約であるログが元の行とずれる可能性を抱えます。

**決定。** 読むときに組み立てます。5 つの小さな問い合わせ（自分の投稿への返信、自分のスレッドへの新規投稿、自分の投稿へのいいね、自分のスレッドへのいいね、自分のスレッドの保存）でそれぞれ直近の行を取り、統合・並べ替えして 12 件に切ります。保存する状態は `User.notificationsSeenAt` だけで、パネルを開いたときに `POST /api/notifications/seen` が更新します。

**結果。**

- 書き込み経路は変えず、埋め戻しも不要で、受信箱がフォーラムと食い違うこともありません。投稿を削除すれば通知も消えます。何も複製していないからです。
- ログイン利用者のページ描画ごとに 5 つの索引付き問い合わせが走ります。学校の規模では見えませんが、遅くなったら最初にキャッシュする対象です。
- 直近の出来事しか存在しません。履歴ページも、出来事ごとの既読フラグも、メール通知もありません。パネルは一瞥のためのもので、記録ではありません。
- 「既読」は粗い単位です。パネルを開くとその時点までのすべてが既読になり、開いている間に届いた通知は次に開いたときに見えます。

**検討した代替案。** 行ごとの既読フラグを持つ `Notification` テーブル（正確だが書き込み経路が 5 つ増え、ずれる危険がある）、RSC のペイロードだけで通知を出す（ページをまたいだ未読数が出せない）、外部サービス（数個の JOIN のために依存を増やす）、新着のポーリング（バックグラウンド処理の基盤がまだない）。

**見直す条件。** 出来事ごとの既読状態、メールダイジェスト、すべての通知を見るページのいずれかが求められたとき、または組み立ての問い合わせがページで一番遅い処理になったときです。

## ADR-0026 — 投稿者は自分の投稿を削除でき、削除は必ず見える場所に着地する

**文脈。** `isDeleted` を立てられるのはモデレーターだけでした。間違った答えや誤字、個人情報を書いてしまった生徒には、自分で取り消す手段がありません。自分を通報して待つしかない状態でした。さらに削除の流れは半分しか正直ではありませんでした。削除済みの投稿はプレースホルダーとして描画される一方、その本文は RSC のペイロードに載ったままブラウザへ届いていました。削除後のリダイレクトもスレッド先頭へ戻すだけで、何が変わったのか分かりませんでした。

**決定。**

1. `POST /api/posts/[id]/delete` と `POST /api/threads/[id]/delete` は、`MODERATOR` / `ADMIN` に加えて投稿者本人も受け付けます。判定は 1 行です: `isModerator(user) || authorId === user.id`。
2. 削除済みの投稿は言語に合わせたプレースホルダーとして描画し、本文はクライアントへシリアライズする**前**に空文字へ置き換えます。返信はプレースホルダーの下に残り、本文・いいね・返信・通報・削除の操作だけが消えます。
3. 投稿を削除した後のリダイレクト先は `/t/<threadId>#p-<postId>` です。自分の投稿が置き換わったプレースホルダーに着地し、アンカーの明滅でその場所が示されます。
4. 確認ダイアログは通知パネルと同じく、テーマのクラスを付けたうえで `<body>` へポータルします。コメントツリーの中では祖先のクリップや包含ブロックの影響を受けますが、`<body>` からなら常に画面全体を覆います。

**結果。**

- 本人による削除は即時で、モデレーターの起床を待ちません。監査行には実行者が残るため、誰が何を消したかはモデレーターから見えます（`post.remove`、`thread.remove`）。
- 内容は論理削除のままです。説明責任のため行と本文はデータベースに残ります。削除済みの行については、本文がサーバーから出ないだけです。
- スレッドの最初の投稿を削除しても、タイトルと返信は残り、ルートだけがプレースホルダーになります。スレッド自体の削除は別の操作です。
- UI から削除を元に戻すことはできません。復元にはモデレーターとデータベースの書き込みが要ります。14 歳の生徒にとっても教員にとっても「削除」の意味をそろえるための、意図的な非対称です。

**検討した代替案。** 物理削除（モデレーションの証拠が消える）、モデレーター限定の削除（筋は通るが、生徒に自己通報して待つ習慣を教えることになる）、CSS だけで本文を隠す（テキストはブラウザに届いたまま。最初に出した版がこれで、ここで直しました）。

**見直す条件。** 投稿から 10 分程度の取り消し猶予が欲しいと言われたとき、または本人による削除が通報前の証拠隠滅に使われていると分かったときです。

## ADR-0027 — ライブ更新はポーリングとクライアント側の突き合わせで作る（WebSocket は使わない）

**文脈。** 同じスレッドを開いている 2 人が、再読み込みなしで互いの投稿を見られるべきです。最初の版はバージョン探索をポーリングして `router.refresh()` を呼んでいました。コードとしては正しく見え、ページも実際に再描画されていました。しかし他の人の返信は画面に現れず、「新着」の点滅は何もないのに走っていました。3 つの別々の誤りが 1 つの症状を作っていました。

1. `CommentSection` はツリーを `useState(initial)` で保持しています。React はその初期値の後からの変更を無視するため、更新のたびに新しいツリーが渡されても、コンポーネントは最初のツリーを描き続けます。サーバーコンポーネントは更新され、コメントは更新されませんでした。
2. 探索は作成時刻だけを比べていました。編集も論理削除も（`UPDATE` であり、何も作りません）この数値を動かしません。
3. 点滅は 900 ミリ秒待ってから id を差分していました。それより遅い描画は取りこぼします。

**決定。**

- ポーリングを続けます。`/api/pulse` は `Post.updatedAt`、`Thread.updatedAt`、最新のいいね・保存・通報の行の最大値を返します。そのために `Post` と `Thread` に `@updatedAt` を追加しました。
- 更新は `useTransition` の中で行い、点滅はトランジションが落ち着いたときに当てます（トランジションが pending にならない場合に備えてタイムアウトも併用）。判定経路に固定の待ち時間は置きません。
- 一覧の各項目に安定した id を与えます（カードと行は `t-<threadId>`、投稿は `p-<postId>`）。「何が新しいか」は集合の差であって、文書全体の再描画ではありません。
- サーバーの props を影で持つ状態は明示的に突き合わせます。コメントは更新後のツリーを採用しつつ、ローカルにしかないコメントを残します。いいね/保存ボタンは自分のリクエストが飛んでいる間を除いてサーバーの数値を採用します。突き合わせは `src/lib/comment-merge.ts` に置き、単体テストを付けます。ここが実際に壊れた場所だからです。

**結果。**

- 新しい基盤は不要です。WebSocket サーバーも SSE のエンドポイントも常駐ワーカーもありません。コストは開いているタブごとに 12 秒あたり 1 回の小さなリクエストと、変化があったときのルート全体の再取得です。
- ページは最大 12 秒遅れます。学校のフォーラムとしては意図した妥協です。即時性が要件になったら SSE とファンアウトが要りますが、この配備にはありません。
- 変更された行だけでなくルート全体を取り直します。このデータ量では問題になりません。ボードページが重くなったら最初に見直す点です。
- 非表示のタブはポーリングしません。入力欄にフォーカスがある間は更新を抑止するので、書きかけの下書きが取り上げられることはありません。

**検討した代替案。** WebSocket / SSE（即時だが常駐サーバーとファンアウトが要る）、固定待ち時間で点滅するポーリング（最初に出した版。遅い描画を取りこぼす）、変化のたびに `key={signature}` でコメント欄を作り直す（単純だが、更新にまだ含まれていないコメントが消え、折りたたみ状態も失われる）。

**見直す条件。** ページに 1 秒未満の反映が必要になったとき、ボードページの再取得コストが数ミリ秒を超えたとき、12 秒の遅れで会話が壊れて感じるとの声が出たときです。
