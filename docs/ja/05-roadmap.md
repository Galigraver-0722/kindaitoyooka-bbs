# ロードマップ

> 日本語版です。英語版が正本です: [English](../05-roadmap.md)

見積もりは、1 人の開発者が週 8〜10 時間働き、試験週間と文化祭には使えないという前提です。幅を持った目安として扱い、約束とは考えないでください。

## フェーズ 0 — 計画と骨格の構築

**状態: 完了（2026-10-24）。**

成果物:

- プロダクトブリーフ、スコープ、アーキテクチャ、データモデル、ルートの契約、安全計画、運用
  手順書、意思決定ログ、学習パス、未決事項。
- 動く Next.js アプリケーション: 登録、ログイン、ボード、スレッド、返信、通報、モデレーション、
  ロック／削除、シードデータ。
- 公開 GitHub リポジトリ、MIT ライセンス、アプリをビルドする CI。

終了条件: `pnpm build`、`pnpm lint`、手作業のエンドツーエンドの流れがすべて通る。

## フェーズ 1 — ベータを開いても安全な状態にする（2 週間）

目標: 招待した生徒 20 人が 2 週間使い、データ事故も安全上の事故も起こらない。

成果物:

1. 永続ディスク付きの VPS で、HTTPS のドメインに配備する。
2. SQLite を毎日別の場所へバックアップし、復旧演習を 1 回行う。
3. レート制限: IP + ユーザー名ごとに 10 分あたりログイン 5 回、アカウントごとに 1 時間あたり
   投稿 10 件、1 日あたり通報 20 件。
4. `AuditLog` テーブルを作り、削除・ロック・通報処理の書き込みを、行為者と時刻付きで記録する。
5. ボードページと最近の活動にページネーション（1 ページ 20 件）。
6. プライバシー通知、コミュニティルール、モデレーション方針のページを平易な英語で用意する。
7. データベース接続を確認する `GET /health` エンドポイント。
8. デモ利用者を削除し、実際の管理者アカウントを作成し、すべての認証情報を更新する。
9. モデレーターへの説明: 何を削除し、何をエスカレーションし、どのくらいで対応するか。
10. エラー監視（Sentry の無料枠、または簡単なログ集約）。

終了条件:

- ベータ参加者が、助けなしで一連の操作を完了できる: ボードを探す、登録する、投稿する、返信する、通報する。
- ベータ期間中、48 時間を超えて未処理の通報が 0 件。
- 復旧演習が成功し、復旧したサイトで同じスレッドが読める。
- 通常利用で `database is locked` エラーが出ない。

## フェーズ 2 — 役に立つ状態にする（3〜4 週間）

目標: モデレーターが使い方を説明しなくても、掲示板が質問に答える。

成果物:

- スレッドと投稿をまたぐ検索（まず SQLite FTS5。必要なら Postgres へ）。
- メール確認とパスワード再設定。または、担当教員が承認した手作業の復旧手順を文書化する。
- 利用者プロフィール: ユーザー名、参加日、最近の投稿（個人情報は載せない）。
- 未読表示、または週次のダイジェストメール。
- ボードごとのタグ（`question`、`event`、`lost`、`club`）。
- 短い時間内に限ったスレッド編集と、「編集済み」の表示。
- 印刷や保存のために、スレッドをプレーンテキストで書き出す機能。

終了条件:

- 代表的な 10 個の問い合わせで、検索が関連する結果を返す。
- 2 週間の観測期間で、スレッドの 60% 以上が 48 時間以内に返信を得る。
- データベースに直接触れずにパスワードを復旧できる。

## フェーズ 3 — 学校の承認と公開（3〜4 週間、暦に依存）

目標: 無断のサイトではなく、学校生活の一部として認められる。

成果物:

- 学校の管理職による書面の承認と、名前の分かる担当教員。
- データ取り扱いの合意: 何を、どこに、いつまで保存し、誰が読めるか。
- 担当教員が署名した、事故対応とエスカレーションの手順。
- アクセシビリティの確認: キーボード操作、フォーカス表示、コントラスト、スクリーンリーダー用ラベル。
- 学校が求める場合の日本語化（`docs/ja/08-decision-log.md` を参照）。
- 想定ピークの 3 倍の負荷試験（例: 同時閲覧 100 人）。
- 公開計画: 集会での告知、QR コード付きポスター、教員や部活動の代表による「何でも聞いてください」スレッドのシード。

終了条件:

- 承認が文書化され、プロジェクトと一緒に保管されている。
- 最初の 2 週間、モデレーターが当番に入る。
- ロールバック計画を試験済み: 15 分以内に以前のビルドへ戻せる。

## フェーズ 4 — 本番での最初の学期（継続）

- 週次の指標レビュー: 登録数、週間アクティブ、未回答スレッド、通報対応時間、モデレーターの作業時間。
- 月次の復旧演習と依存関係の更新。
- 四半期ごとの、担当教員との方針レビュー。
- 機能の追加・削除の理由が分かる、公開された変更履歴。

## フェーズ 5 — 成長のための機能（需要が確認できた場合のみ）

会議での熱意ではなく、観測された行動で優先順位を決めます。

| 機能 | 作るきっかけ |
| --- | --- |
| PWA のインストール／オフライン閲覧 | モバイルからのアクセスが 70% を超え、再訪が定着している |
| リアクション | 「+1」だけの返信が全投稿の 10% を超える |
| 画像アップロード | ポスター画像なしでは部活動の行事スレッドが成立しない、**かつ** 画像レビューを捌けるモデレーション体制がある |
| ボード単位のモデレーター | 全体キューが 1 日 30 分を超える |
| 公開 JSON API | 2 つ目のクライアント（モバイルアプリ、案内端末）が実際に作られている |
| 連合 | 単一の学校では永久に不要 |

## 意図的に先送りすること

- リアルタイムのものすべて。
- AI モデレーション。フラグ付けはできても、判断は人間が行います。
- 匿名投稿。この規模では、モデレーション上の利点なしに説明責任だけを失います。
- 学外からの自由な登録。開かれた登録はスパムと見知らぬ人を招きます。

## スケジュールのリスク

| リスク | 初期の兆候 | 対応 |
| --- | --- | --- |
| 試験週間 | 誰も投稿しない | 機能開発を止める。沈黙を失敗と解釈しない |
| 文化祭 | アクセスの急増、モデレーション負荷 | 重要でない変更を凍結し、キューに人を付ける |
| 担当教員の異動 | 承認が危うくなる | すべてを文書化し、早い段階で 2 人目の助言者を探す |
| 保守担当の卒業 | バス係数 1 | 1 年目に後任を育て、手順書を最新に保つ |
| スコープの膨張 | 「画像だけ追加して」 | Won't の一覧を読み直す。画像は安全プロジェクトであり、機能ではない |
